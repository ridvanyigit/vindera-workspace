### Major

**F-MAJOR-1 — the default (120/min) and shared application (300/min) rate limits do nothing** · area: backend API · owner: backend
- What happened: only the per-route limits on `POST /chat` (20/min) and `POST /deals/scan` (30/min) return 429. Everything else is unlimited, and the "shared 300/min budget that stops a flood of bad tokens" described in `core/rate_limit.py` and `docs/LAUNCH-PROGRESS.md` (Phase 1) is not enforced.
- Expected: 429 after 120 requests/min per IP on any route, and after 300/min in total (also for unauthenticated requests).
- Reproduce: start the backend (`ENVIRONMENT=development`, any settings), then in one minute send 140 `GET /healthz`, or 140 `GET /api/v1/expenses/` with an admin token, or 320 unauthenticated `POST /api/v1/chat/`: every answer is 200 / 200 / 401, never 429. `POST /chat` x25 gives 5 x 429, `POST /deals/scan` x35 gives 5 x 429 (so slowapi itself works).
- Evidence: 140 requests each to 4 routes -> `{200: 140}`; 320 unauth -> `{401: 320}`; installed versions `slowapi 0.1.10`, `fastapi 0.141.1`, `starlette 1.6.0`. Probable cause (not verified): `SlowAPIMiddleware` cannot resolve the endpoint of routers mounted lazily by FastAPI 0.141 (the same lazy `include_router` behaviour that `LAUNCH-PROGRESS.md` mentions for `app.routes`), so the default/application limits are skipped.
- Impact: JWT-shaped bad tokens can be sent in bulk and each one costs a Supabase auth call; login/brute-force protection relies on Supabase only. Authentication is still required for every data route.
- Suggested fix: apply the limits in a way that does not depend on route discovery (a dependency on the routers, or an explicit middleware), and add a test that fires 121 requests.

### Minor

**F-MINOR-1 — `CORS_ALLOWED_ORIGINS=*` is accepted in production** · config/backend
- Production start-up refuses localhost origins but not `*`: the container runs and answers `access-control-allow-origin: https://evil.example` (echo) with credentials true for any origin. `main.py` says a wildcard must never happen.
- Reproduce: `docker run -e ENVIRONMENT=production ... -e CORS_ALLOWED_ORIGINS='*' vindera-backend` then `curl -H 'Origin: https://evil.example' .../healthz -D -`.
- Suggested fix: add `*` to the "unsafe production configuration" checks.

**F-MINOR-2 — two migrations have no header comment** · SQL/docs
- `20260916082200_remote_schema.sql` (pulled dump) and `20260917084516_add_sold_at_column.sql`; CLAUDE.md asks for a "why" header. Both predate the hardening branch and are already applied; do not edit them (add a note in a doc instead).

**F-MINOR-3 — `storefront_listings` carries write privileges for `anon` and `authenticated`** · SQL
- `has_table_privilege` shows INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER on the view for both browser roles. Writes are refused today only because a join view is "not automatically updatable" (55000). One future simplification of the view (single table, no join) would turn this into a real hole. Suggested fix: a new migration `REVOKE ALL ... FROM anon, authenticated; GRANT SELECT ...` on the view.

**F-MINOR-4 — unknown JSON fields are silently ignored** · backend
- The plan expects 422. `POST /deals/scan {"asin":"B0NOPROD01","bogus":1}` -> 202, `POST /expenses/` with `"bogus":1` -> 201, `PATCH .../status {"bogus":1}` -> 200, `POST /deals/manual` with `totally_unknown_field` -> 201. A misspelled field name is dropped without a word. Suggested fix: `model_config = ConfigDict(extra="forbid")` on the request models.

**F-MINOR-5 — the API stores a category that is not in the canonical list** · backend
- `POST /deals/manual` with `"category": "Not A Category"` -> 201 and stored as such. Only the Manual Entry dropdown restricts it. The dashboard filters and the category audit assume the canonical 8. Suggested fix: validate against `CANONICAL_CATEGORIES` or map to "Other".

**F-MINOR-6 — jobs interrupted by a restart are closed only if older than 15 minutes** · backend
- `fail_interrupted_scan_jobs` runs once at start with a 15-minute cutoff and never again. A scan that was `running` 2 minutes before a redeploy stays `running`/`queued` in the dashboard until some later restart. With one uvicorn worker every `queued`/`running` row at start-up belongs to a dead process. Reproduce: insert `scan_jobs` rows `running` (started 2 min ago) and `queued` (created 1 min ago), restart the backend: both stay unchanged (rows 20 min old are closed).

**F-MINOR-7 — misleading 409 for `quantity` > 1 with status `pending`** · backend
- `POST /deals/manual` with `quantity: 3, status: "pending"` answers "This product already has an open scan or pending deal" although none exists; the real reason is that three pending rows would break the one-open-row rule. Suggested fix: reject `quantity > 1` for `pending` with a specific 422 text.

**F-MINOR-8 — an extreme purchase date causes an unhandled 500** · backend
- `PATCH /deals/{id}/status {"status":"bought","purchase_price_actual":10,"purchased_at":"9999-12-31T23:59:59Z"}` -> `OverflowError` inside `return_by_date` -> HTTP 500. Years 0001, 1900 and 2100 are accepted without complaint. Suggested fix: bound `purchased_at` (for example not in the future, not before 2000) and catch the overflow as 422.

**F-MINOR-9 — no request-body size limit anywhere** · backend/config
- A 50 MB JSON body to `/chat` is read completely before the 422 (0.28 s); 100 000-level nested JSON to `/deals/scan` gives a 500 with a logged traceback (backend stays up, RSS grew to 284 MB). Neither uvicorn nor the Caddyfile (`request_body { max_size ... }`) limits it. Suggested fix: a size limit in Caddy for the API site (for example 1 MB, larger for nothing) and/or a middleware.

**F-MINOR-10 — modal and control accessibility** · frontend
- The Sold / Bought / Return modals have no `role="dialog"` / `aria-modal`, do not close with Escape or a backdrop click (only the Cancel button), and `/admin` has 3 icon-only buttons without accessible name (for example the theme toggle) and 3 unlabeled inputs, Manual Entry 7 (score sliders).

**F-MINOR-11 — the deployed frontend still points its API at `http://localhost:8000`** · config/manual step
- Live bundle and CSP (`connect-src ... http://localhost:8000`) show `NEXT_PUBLIC_API_URL` was not set on Vercel at build time. Expected before the backend goes live; it must be set (DEPLOY section 9) and the site redeployed, otherwise the production admin cannot reach any backend.
